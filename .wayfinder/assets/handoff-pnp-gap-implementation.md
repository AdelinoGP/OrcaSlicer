# Handoff: PNP-side gaps blocking the OrcaSlicer-frontend fork

Audience: a planning session in `F:\slicerProject\pinch_n_print` using the spec-packet workflow (`/spec-packet-generator`, then `/spec-review --preflight`, then `/swarm`). Source: [feature-coverage inventory](001-pnp-feature-coverage-inventory.md) (ticket 001 of the fork's wayfinder map), verified against the live release binary and pnp docs on 2026-07-16.

Context: the fork replaces OrcaSlicer's in-process slicing with `pnp_cli slice` shell-outs (v1 scope: slice + preview, single plate per invocation, Windows-first). Each item below is a PNP capability gap the fork's GUI currently has UI surface for.

> **Framing locked by fork ticket 012 (2026-07-17) — read before packeting.** These items are **scheduled prerequisites, not "either/or" choices.** PNP features are implemented in parallel with the fork's roadmap, so each gap closes before the fork needs it. The fork ships **zero UI restrictions and no capability gate**: it does not hide, disable, or block any control for any gap below. Earlier wording offering the fork a hide-the-UI escape hatch (items 3, 5, 6) is withdrawn — the fork exposes all of these surfaces unguarded, so every item here must actually land.

> **Corrected by fork ticket 013 (2026-07-17): the fork has NO gap-communication channel to the user at all.** This note previously said the fork's only such channel was "a slice-time warning derived from its ticket 005 config-translation table". Ticket 013 decided that warning vector is **written to a log, never shown** (`<data_dir>/pnp-config-warnings.jsonl` + one line in Orca's log) — it is a dev instrument for growing the mapping table, not a user surface. So there is no warning, no dialog, no notification, and no capability gate anywhere in the fork. **Every item below fails silently from the user's point of view**: a Klipper user gets Marlin G-code, a raft user gets no raft, a non-uniformly-scaled object gets a raw loader error, with nothing on screen explaining why. This raises the stakes on the scheduling promise — the fork is not merely undefended, it is *mute*.

## Items

1. **Print-time estimation** — `estimated_print_time_s` is hardcoded 0 in `crates/slicer-gcode/src/emit.rs` (`PrintMetadata`); no kinematics/acceleration model exists. Orca's preview and sidebar show per-feature/per-layer time. Needs an estimator (even a simple feedrate-distance model beats 0) surfaced in G-code metadata. High priority — visible on every slice.

   **Note from fork ticket 011 (2026-07-17):** the fork's *preview* does not depend on this — Orca's `GCodeProcessor` recomputes times from parsed moves and ignores `; estimated printing time` on load, and `GCodeViewer::render_legend` hides the estimated-time section outright when the time is 0 (`show_estimated_time = total_estimated_time > 0.0f && ...`), so preview degrades cleanly rather than showing `0s`. What this item actually unblocks is (a) time *accuracy* — which is really item 10's `machine_max_*` passthrough — and (b) items 2 and 15, both of which are strictly downstream of a real estimator.
2. **`slice_stats` progress event** — reserved in `docs/09_progress_events.md` schema 1.2.0 (`gcode_prediction_seconds`, `gcode_weight_grams`, `gcode_filament_length_mm`, `layer_count`, `first_layer_height_mm`) but not emitted. Implementing it lets the GUI get stats without parsing G-code. Natural companion packet to item 1.

   **Amended by fork ticket 011 (2026-07-17) — the reserved five fields are insufficient; the fork now depends on this event for weight.** Orca's `PrintStatistics` (`src/libslic3r/Print.hpp`), which the fork must fill because the export path that filled it is deleted, needs more than one grams figure: `total_used_filament` (mm of filament), `total_extruded_volume` (mm³), per-extruder `filament_stats` (a `map<size_t, double>` of volumes), and `total_toolchanges`. Add per-extruder volume breakdown and toolchange count to the event. **Do NOT add a cost field** — fork ticket 011 decided cost is computed fork-side from Orca's own preset (`filament_cost`, `time_cost`), since it is Orca pricing math over a volume the fork already has; pnp should not import Orca's pricing model. Weight, length and prediction come from pnp; cost does not.
3. **Standalone raft** — no raft-under-part feature; only `support_planner`'s `support_raft_layers` (default 0) exists. Orca UI exposes raft controls.

   **Corrected + reframed by fork ticket 012 (2026-07-17).** Ticket 001's "❌ no raft" was derived from the live `module config-schema` probe (implemented modules only) and **missed the existing design work** — this is not an unplanned gap. Already on the pnp side: **ADR-0009** (`docs/adr/0009-raft-as-layer-infill-role.md`, status *Proposed*) settles the direction — `raft-default` is a region *synthesizer*, not a renderer; raft polygons render through whichever `Layer::Infill` module claims `claim:raft-fill`, via a new `ExtrusionRole::RaftInfill` — and **`docs/specs/raft-default-module.md`** is a design sketch whose central question (the output carrier) is explicitly left open for implementation time. Depends on `docs/specs/support-modules-orca-port.md` §C6 landing `SupportPlanIR.raft_plan`. **The fork does NOT hide the control** (ticket 012) — that escape hatch is withdrawn. Interim behaviour is already specified by fork ticket 005's mapping row: `raft_layers` → `support_raft_layers` (copy), warn when >0 with supports off.
4. **Multi-material end-to-end proof** — plumbing exists (wipe-tower module, `T<n>` tool changes, per-region extruder via 3MF modifier config, filament colour arrays) but open backlog items block exposure: TASK-210 (support_filament / support_interface_filament routing), TASK-211 (real-fixture T0/T1 G-code E2E, currently synthetic-only), TASK-212 (object-scoped printer-key sidecar allowlist only partially populated). These are existing pnp backlog tasks — packet them rather than re-scoping.

   **Reframed by fork ticket 012 (2026-07-17): the fork exposes multi-material fully, with no restriction and no warning.** Consistent with ticket 004's "let PNP try" — the gap is *unproven*, not absent. There is no fork-side safety net: a user with an AMS/multi-filament printer will exercise this path on day one and any E2E defect surfaces as a bad print with no hint that it is an unproven path. Raises priority. Note for scoping: the fork's would-be gate was `Sidebar::show_SEMM_buttons()` (the "+ add filament" button), **not** extruder count — BBL/AMS printers are **1 nozzle + N filaments**, so `nozzle_diameter.size()` is 1 and multi-material rides filament count, not extruder count. If pnp's MM model assumes multi-*extruder*, that assumption is wrong for the largest printer population the fork exposes.
5. **G-code flavor selection** — `gcode_flavor` is hardcoded `marlin` in `crates/slicer-gcode/src/serialize.rs` CONFIG_BLOCK; no Klipper/RepRap variants. ~~Low priority if the fork restricts printer profiles to Marlin, but decide deliberately.~~

   **Reframed and re-prioritised by fork ticket 012 (2026-07-17): the fork does NOT restrict printer profiles.** The "restrict profiles to Marlin" escape hatch is withdrawn — it would have deleted ~60% of the bundled printer library. Of the 416 bundled profiles that declare a flavor: **klipper 233, marlin 92, marlin2 59, reprapfirmware 31, repetier 1** (BBL's 73 machines are all marlin via a common base; Creality is mostly klipper). The fork exposes all 5 UI-visible flavors and warns via ticket 005's `unsupported-feature` classification. **Mitigating facts that keep this below items 1/2 despite the exposure:** Klipper — the largest group — accepts Marlin G-code, and `machine_start_gcode`/`machine_end_gcode` are Tier-A identical keys that pass through to PNP unchanged, so each profile's printer-specific setup survives regardless of flavor. The genuinely divergent dialects are reprapfirmware (31) and repetier (1). Suggested order: klipper first (largest population), then reprapfirmware.
6. **Non-uniform scale support** — `slicer-model-io` loader rejects non-uniform-scale transforms (`NonUniformScaleUnsupported`). Orca's GUI freely applies non-uniform scaling. **Confirmed PNP-side by fork ticket 004 (2026-07-16):** the fork will NOT bake scale at export. ~~its GUI blocks slicing with an error until PNP lifts the restriction~~ — **superseded by fork ticket 012 (2026-07-17): the fork implements NO check at all**, neither a UI restriction nor a slice-time block, on the expectation that PNP lifts this restriction (bake scale into vertices at load) before the fork is user-visible. **This is now a hard scheduled prerequisite, not a gap the GUI defends against** — until it lands, a non-uniformly-scaled object reaches pnp_cli and fails with a raw loader error the fork does not pre-empt. Raised to high priority: Orca's scale gizmo and its "Uniform scale" checkbox (default on, freely unticked) make this trivially reachable by any user.
7. **Multi-plate 3MF** — **Won't-fix, confirmed by fork ticket 004 (2026-07-16):** the fork hands PNP one plate per invocation as a plate-local-origin single-`<build>` 3MF. Close this item.
9. **Orca per-object config-key parity in the 3MF sidecar parser** — fork ticket 004 (2026-07-16): the fork writes `model_settings.config` per-object/per-volume config deltas untouched, using Orca key names, and also writes per-volume extruder/filament assignments as-is. PNP's sidecar parser should accept/translate Orca per-object key names (mirroring the global-key translation table the fork uses, its ticket 005); until then unknown per-object keys are silently ignored. Medium priority — per-object overrides silently no-op otherwise.
10. **Viewer-config passthrough keys in CONFIG_BLOCK** — fork ticket 007 (2026-07-16): emit `printer_model` (any non-"Bambu Lab" value; guards Orca's `s_IsBBLPrinter` tag-table derivation on drag-in), `filament_density`, `filament_cost`, `printable_area`, `nozzle_diameter`, and the `machine_max_acceleration_*`/`machine_max_speed_*`/`machine_max_jerk_*` family in the CONFIG_BLOCK (`crates/slicer-gcode/src/serialize.rs` padding or host raw_config passthrough). Orca's viewer computes time/mass/cost itself from moves + these keys; without them it falls back to defaults (approximate times, default-density grams). Low effort, low risk — the serializer already writes raw_config keys verbatim.

    **Upgraded to MANDATORY by fork ticket 011 (2026-07-17) — there is no fork-side workaround.** `GCodeProcessor::process_file`'s producer pre-pass, for `EProducer::OrcaSlicer`, does `config.apply(FullPrintConfig::defaults())` → `config.load_from_gcode_file(filename)` → `apply_config(config)`. It starts from **defaults and discards anything pre-applied**, so the fork cannot hand the processor its in-memory preset — everything the processor knows must arrive via the CONFIG_BLOCK. PNP's header line `; OrcaSlicer-compatible output generated by Pinch'n'Print` matches the `Producers` table (`{ EProducer::OrcaSlicer, SLIC3R_APP_NAME }`), so this branch *is* the fork's ingestion path. `machine_max_*` therefore solely determines time accuracy, and `filament_density` solely determines the per-role grams in `used_filaments_per_role` (computed during parse, in `UsedFilaments::process_role_cache`). `filament_cost` is no longer needed for the fork's own preview (cost moved fork-side per item 2's amendment) but is still wanted for standalone drag-in of pnp G-code. Also note `s_IsBBLPrinter` **defaults to `true`**, and `process_file` only overwrites it inside `if (printer_model_opt && !value.empty())` — so `printer_model` is what makes drag-in safe without the fork's forced override.
11. **Graceful cancel** — fork ticket 003 (2026-07-16): pnp_cli has no cancellation support (no signal handling in `crates/pnp-cli`). v1 fork kills the child outright; wanted: exit cleanly on stdin close or SIGINT/CTRL_BREAK_EVENT (Windows-first) so the GUI can do graceful-cancel-with-kill-timeout. Low priority for v1 (kill is safe — pnp_cli is stateless), quality-of-life later.
12. **Layer count in progress stream** — fork ticket 006 (2026-07-17): the JSONL stream never reports total layer count, so the fork's progress bar scales `layer_index` against a GUI-side estimate (model height ÷ layer height). Add `layer_count` to `phase_start(per_layer)` or ship the reserved `slice_stats` event (overlaps item 2) to make percent exact. Low effort.
13. **Support-preview geometry query** — fork ticket 008 (2026-07-17): Orca's support-painting gizmo (`GLGizmoFdmSupports`) renders a live support-preview overlay while painting by calling `PrintObject::generate_support_preview()`, which runs the real `posSlice` + `posSupportMaterial` steps in-process. The fork deletes that path (it's the only GUI consumer of native slicing *output*), so v1 paints supports blind — the user sees generated supports only after a full slice. Wanted: a way for the GUI to ask PNP for support geometry for one object without a full slice + G-code emit (e.g. a `pnp_cli support-preview` verb, or a slice mode that stops after the support stage and emits support polygons/meshes). Non-trivial — needs a partial-pipeline entry point and a geometry-out format. Low priority for v1 (UX regression, not a blocker); revisit once slice+preview is stable.

14. **Thumbnail block: broken wire format + single-PNG CLI** — fork ticket 011 (2026-07-17). **Two defects, one packet.** This item *replaces* the "Thumbnails: not a gap" entry previously under "Not gaps" — that assessment was wrong.

    a. **The emitted block is unparseable by anything but PNP.** `serialize_thumbnail_block` (`crates/slicer-gcode/src/thumbnail.rs`) emits `; THUMBNAIL_BLOCK_START` / bare base64 / `; THUMBNAIL_BLOCK_END`. Orca (`src/libslic3r/GCode/Thumbnails.hpp`, `export_thumbnails_to_file`) **nests tag lines inside those outer sentinels**: `; <tag> begin <W>x<H> <encoded_len>`, base64 wrapped at 78 cols, `; <tag> end`. PNP omits the inner `begin`/`end` lines deliberately (source comment: so its roundtrip test decodes the region cleanly) — but every real consumer keys on `; thumbnail begin`; that is the `BEGIN_MASK` in Orca's own reader (`GUI_App::gcode_thumbnails_debug`) and the PrusaSlicer-lineage convention firmware and print hosts parse. Fix the format; fix the roundtrip test to parse the real format rather than the reverse.

    b. **`--thumbnail` takes one PNG; Orca's contract is a list.** `thumbnails` is a `coString`, default `"48x48/PNG,300x300/PNG"`, format `"XxY/EXT, ..."` (`thumbnails_format` is legacy, folded into the per-entry `/EXT` suffix by `handle_legacy_composite`); `export_thumbnails_to_file` invokes its callback once per requested size. Across `resources/profiles/`, 190 machine profiles pin a format: 182 PNG, 3 QOI, 3 ColPic, 2 JPG. Five formats span three wire shapes — PNG/JPG/QOI base64 with tags `thumbnail`/`thumbnail_JPG`/`thumbnail_QOI`; BTT_TFT (`thumbnail_BIQU`) a `;WWWWHHHH\r\n` hex header + raw payload; ColPic (`thumbnail_QIDI`) `;gimage:` for the first and `;simage:` for subsequent.

    **Decided split (fork ticket 011 — both halves now locked):** pnp owns embedding *and* encoding. The fork (the only side with a GL context) renders each requested size and encodes it **as PNG only**. `pnp_cli` grows a **repeatable** thumbnail argument carrying `(path, WxH, target format)`, decodes the PNG, re-encodes to the target format, and owns the wire framing: base64, 78-col wrap, outer sentinels, inner begin/end lines, and the ColPic/BTT special shapes. Rejected: fork encoding via Orca's existing `compress_thumbnail` and passing bytes+tag (cheaper, but splits format knowledge across both codebases); rejected: raw RGBA transfer (large temp files, GL's bottom-up row order leaks into pnp).

    **Stage it PNG-first.** PNG is a passthrough (the decode/re-encode collapses to a copy) and covers **182 of the 190** profiles that pin a format — i.e. nearly the whole fork-visible surface. Ship PNG-only, then add QOI / ColPic / JPG transcodes as a follow-up. The tail is the expensive part: ColPic is a bespoke RGB565 palette/RLE codec (`ColPic_EncodeStr`, 512px cap, aspect preserved) and BTT_TFT is RGB565 hex text with `\r\n` endings — neither is a standard library format, and both need porting from `Thumbnails.cpp` rather than pulling a crate. **Row order:** PNG is the only Orca encoder that does *not* flip the bottom-up GL buffer, so PNGs arriving from the fork are already top-down — the transcoders must not re-flip.

    Medium priority — the fork ships v1 without thumbnails cleanly (they are simply absent), so this gates completeness, not the seam.

15. **M73 progress + `; filament used [g]` comments** — fork ticket 011 (2026-07-17). **Decided: pnp emits M73 itself** during G-code emit, off item 1's estimator; the fork stays out of post-processing (its ingestion keeps `finalize(false)` and never calls `run_post_process`). Rejected alternative: pnp plants Orca's `_GP_FIRST_LINE_M73_PLACEHOLDER` / `_GP_LAST_LINE_M73_PLACEHOLDER` comments and the fork triggers Orca's own injector via `set_print` + `finalize(true)` — cheaper, but makes pnp's output depend on Orca to become printable.

    Scope: `M73 P<percent> R<remaining_min>` lines through the file (Orca's own masks, for reference: `"M73 P%s R%s\n"` Normal, `"M73 Q%s S%s\n"` Stealth), plus the `; filament used [g]` comment block — Orca's viewer ignores that block on load (it recomputes from moves) but firmware and print hosts read it. Needs cumulative per-line remaining-time tracking, so it is **strictly downstream of item 1**: do not ship M73 before the estimator exists, since a fabricated remaining-time is worse than none. Related Orca key: `disable_m73` (printer preset, `coBool`, default false) — if ever mapped, it belongs in the fork's ticket-005 translation table.

8. **Seam live-path gaps** — TASK-120c: seam-placer reads `resolved_seam` instead of selecting from `PerimeterIR.regions[*].seam_candidates`; rotated-wall replacement can erase sibling walls unless the full region wall set is re-emitted. Existing pnp backlog item; correctness risk on every slice with seam control.

16. **`seam_position: aligned` — no PNP equivalent, and it is Orca's DEFAULT** — fork ticket 013 (2026-07-17). PNP's `seam_mode` accepts `nearest` / `rear` / `random`; Orca's `seam_position` enum is `nearest` / `aligned` / `aligned_back` / `back` / `random`. `nearest`, `back`→`rear` and `random` map 1:1; **`aligned` and `aligned_back` have no PNP equivalent** and fall back to `nearest`.

    **Why this is not the low-priority curiosity fork ticket 005 filed it as.** 005 recorded it as a "candidate future seam mode". But Orca's default is `spAligned` — verified in `PrintConfig.cpp`: `def->set_default_value(new ConfigOptionEnum<SeamPosition>(spAligned))`, with `def->mode = comSimple` (visible in the simplest UI mode). So this is not a fallback that fires for the adventurous user who went looking for seam options; **it fires on every slice by every user who never touched seam settings**, which is most of them. Every such print gets `nearest` seams — scattered, visible on the outer wall — where Orca would have aligned them into a single seam line. This is a *visible print-quality regression on the default path*, not an edge case.

    It is also invisible: fork ticket 013 records it as a `lossy-fallback` in the fork's dev log and shows the user nothing. (013 does make a point of keeping it *loggable* — its non-default filter deliberately does not apply to lossy fallbacks precisely because this one would otherwise be filtered out for being at its default value.)

    Scope: add an `aligned` seam mode to the seam module — accumulate a per-object seam position across layers and snap each layer's seam toward it, rather than choosing per-layer nearest. `aligned_back` (aligned, but biased to the rear) is the same machinery with a starting constraint. Natural companion to item 8 (both are seam-module work, and 8's `seam_candidates` selection is the mechanism `aligned` would choose from) — but note 8 is a *correctness* bug in the existing live path while 16 is a *missing mode*; they are separable.

    **High priority** — highest-visibility item on this list per-slice, since it needs no unusual configuration to hit.

## Not gaps (do not re-implement)

- ~~Thumbnails: PNP's external-PNG-in `--thumbnail` design is fine~~ — **retracted by fork ticket 011 (2026-07-17); see item 14.** The externally-supplied-PNG *direction* is right (the fork has the only GL context), but the block format is unparseable and one PNG cannot express Orca's per-profile size/format list.
- `;TYPE:` annotations, LAYER_CHANGE markers, HEADER/CONFIG blocks: already Orca-viewer-compatible. (THUMBNAIL block: **not** — see item 14.)
- Print-time estimate comments (`; estimated printing time`) and `; filament used` comments are ignored by Orca's viewer on load — it recomputes from parsed moves. Their absence is not what makes the fork's stats wrong; see items 1, 2 and 10.
